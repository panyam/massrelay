# v0.3.0

This release lets one `AppMessage` go to several peers, and stops the relay
from dropping messages without telling anyone. It's a minor bump because the
`AppMessage` wire format changes: `to_client_id` becomes `to_client_ids` on
the same field number, and nothing out there was sending the old field yet.
It also raises how many connections one IP can open at once, which was
quietly refusing the fourth tab of a browser restoring a session.

## Breaking

- **`AppMessage.to_client_ids`** (issue 43, PR 44). The string
  `to_client_id = 3` is now `repeated string to_client_ids = 3`. Each listed
  peer gets the message once, with `to_client_ids` rewritten to hold only its
  own id, so a receiver still tells addressed from room-wide and doesn't learn
  who else was addressed. Ids not in the room come back to the sender as one
  `ErrorEvent{PEER_NOT_FOUND}` naming them all, and the rest are still
  delivered. Before, one absent target meant nothing was delivered.
  Empty still fans out to the whole room.
  - Migration (TS): `sendAppMessage(kind, payload, { to })` takes a string or
    an array, so existing calls keep working. `onAppMessage`'s `toClientId`
    argument is unchanged (this client's id, or empty).
  - Migration (Go): `DeliverAppMessage` takes the new message shape, and its
    error wraps `ErrPeerNotFound` with the missing ids. `CollabRoom.SendTo` is
    gone; use `SendEach`.
- **Slow consumers are evicted** (PR 44). A peer whose 64-event queue fills is
  removed from the room and sent `SessionEnded{reason: "slow_consumer"}`, and
  the others see `PeerLeft` with that reason. Before, the relay dropped events
  to it and kept delivering later ones, so it saw gaps. Now every receiver gets
  an unbroken, in-order prefix of each sender's messages, which is what lets a
  batch A1..A5 reliably land before B1..B5 at every peer.

## Added

- **`RELAY_PER_IP_BURST`** (issue 45, PR 47). How many connections one IP may
  open at once. It defaults to max(3, `RELAY_PER_IP_RATE`), so production goes
  from 3 to 5 and raising the rate raises the burst with it. `CollabClient`
  doesn't retry a refused upgrade, so a fourth concurrent tab used to just fail
  with a 429.

## Changed

- **Over-rate messages get `ErrorEvent{RATE_LIMITED}`** (PR 44), naming the
  dropped `actionId`, instead of vanishing.
- README's Rate Limiting section now lists the real env vars instead of a
  `RateLimitConfig` snippet that didn't match any API.

## Known limits

- An evicted slow consumer's WebSocket stays open until the client closes it,
  since servicekit has no way for a stream to close its own socket yet
  (issue 46).
